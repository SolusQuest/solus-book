# Issue template

Adapt this structure to the project's tracker and language. Omit fields that add no execution value. Follow [Issue workflow](../standards/issue-workflow.md); native tracker metadata belongs in its actual fields.

## Objective

State one independently acceptable outcome and the problem it resolves.

## Context and scope

Describe relevant current behavior, accepted constraints, included work, and useful exclusions. Give deferred work a destination when it matters for planning.

## Acceptance criteria

List observable conditions for acceptance. For an experiment, state the question and resolving evidence instead of promising an unobserved production result.

## Validation

Identify applicable checks or evidence, using the project's actual commands when known. State a genuine unavailable input or unresolved check rather than inventing one.

## Dependencies and implementation notes

Record actual dependencies, expected review boundary, accepted design choices, and useful code paths. Ordinary implementation order does not require separate tracker issues.

## References and open decisions

Link owning documents with the pinning appropriate to their purpose. Mark required material decisions still unresolved; do not describe the issue as implementation-ready until those decisions are settled.

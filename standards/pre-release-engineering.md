# Pre-release engineering

Before a supported external commitment exists, optimize for learning, correctness, and reversible progress. Use the amount of process needed to protect the concrete failure surface. Pre-release status does not remove privacy, authority, destructive-operation constraints, or real consumer obligations.

## Coherent outcomes

An independently acceptable outcome usually fits zero or one tracking issue, one coherent implementation PR, applicable review, and checks chosen from the changed behavior. An authorized local initialization can remain local. Missing initial Git history, issues, or templates should not block that work.

Keep implementation with the contracts, tests, fixtures, and documentation needed to accept it. Split outcomes that are independently useful and verifiable, have independently unblockable dependencies, or require distinct authority decisions. Class names, file names, and implementation order alone are not useful delivery boundaries.

Keep behaviors that jointly maintain an invariant together. A coordination parent should supply useful dependency or closure information. Avoid artificial sub-issues that can only be accepted after each other is complete.

## Reuse and current drafts

Before establishing a durable external contract, persisted format, security mechanism, distribution boundary, or irreversible workflow authority, inspect a bounded set of mature precedents. Record the useful pattern and why a material divergence is needed. Routine reversible changes do not need a research phase.

Maintain one current draft shape for each selected implementation path. Replace affected producers, consumers, validators, fixtures, and docs coherently. Supported alternatives and test implementations are legitimate; obsolete draft readers and speculative compatibility aliases need a real obligation under [Contract lifecycle](contract-lifecycle.md).

## Additional process

Add another PR, review, validation matrix, provenance format, compatibility mechanism, or mutation stage when a concrete risk requires it. Explain the risk and why the simpler path is insufficient. Record a simplification or removal condition when the mechanism is temporary.

Reuse applicable evidence for unchanged inputs. Repeat or broaden checks after changed inputs, failure, or unresolved concerns. A timeout or incomplete run does not justify retrying blindly until green.

Retire completed experiments while preserving useful regressions and concise historical conclusions. Validation infrastructure should support the engineering outcome rather than become a separate certification system.

## Corrections

A later defect normally belongs to the current failing boundary. Preserve historical acceptance and make the smallest coherent correction across the affected behavior. Reopening closed scope, expanding authority, or changing product commitments requires the corresponding owner decision.

When the same coupled path exposes repeated defects, its current owner consolidates known related corrections and checks directly adjacent behavior. Bound that check by observed coupling and the task's authority. Avoid opening a separate issue or PR for every assertion in the same failure; an ordinary correction does not automatically become a comprehensive audit.
